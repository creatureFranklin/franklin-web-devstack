# Internationalisation (i18n)

This devstack has built-in support for **generating static multi-language variants** of your HTML templates at build time.  
No JS framework, no runtime router – translations are baked into the HTML and optionally available in JavaScript via a tiny helper.

---

## How it works

```
src/index.html          (template with {{key}} placeholders)
src/locales/en.json     (English translations)
src/locales/cs.json     (Czech translations)
        │
        ▼  node scripts/build-i18n.mjs
        │
dist/index.html         ← English (default locale, dist/ root)
dist/cs/index.html      ← Czech
```

Each output file has:
- all `{{key}}` placeholders replaced with the locale's translations
- `<html lang="...">` set to the locale code
- `<link rel="alternate" hreflang="...">` tags injected for every locale
- an inline `<script>window.__i18n = {...}</script>` so JS can access translations at runtime

---

## Configuration

Add a `devstackI18n` block to `package.json`:

```jsonc
{
  "devstackI18n": {
    "defaultLocale": "en",        // written to dist/ root (not a subdirectory)
    "localesDir":    "src/locales",
    "siteUrl":       "https://example.com"  // optional – used as base URL in hreflang hrefs
  }
}
```

| Field | Required | Description |
|-------|----------|-------------|
| `defaultLocale` | ✅ | Language code of the default locale. Its output goes to `dist/` directly (no subfolder). |
| `localesDir` | ✅ | Path to the folder containing `*.json` locale files. |
| `siteUrl` | ✗ | Full base URL of the site. Used to build absolute `href` values in `<link rel="alternate">`. If omitted, paths will be relative. |

## Locale files

Create one JSON file per language in `src/locales/`:

```
src/locales/
  en.json   ← English (matches defaultLocale)
  cs.json
```

The file name (without `.json`) is the locale code used everywhere.

### Structure

JSON keys can be nested to any depth. Use dot-notation in placeholders:

```jsonc
// src/locales/en.json
{
  "lang": "en",
  "meta": {
    "title": "My site"
  },
  "hero": {
    "heading": "Welcome!",
    "button":  "Get started"
  }
}
```

```html
<!-- src/index.html -->
<html lang="{{lang}}">
  <title>{{meta.title}}</title>
  <h1>{{hero.heading}}</h1>
  <button>{{hero.button}}</button>
```

> If a key is missing in the JSON, the placeholder is left as-is and a warning is printed to the console during the build.

## HTML placeholders

### Syntax

```
{{key}}
{{section.key}}
{{deeply.nested.key}}
```

Placeholders are replaced in **all `*.html` files** found directly in `src/`.

### Special markers

Add these HTML comments to control where the script injects certain blocks:

| Comment | What gets injected |
|---------|-------------------|
| `<!-- i18n:hreflang -->` | `<link rel="alternate" hreflang="...">` tags for every locale + `x-default` |
| `<!-- i18n:translations -->` | `<script>window.__i18n = {...};</script>` – the full translations object |

If a marker is missing, the script falls back to inserting before `</head>` / `</body>` respectively.

**Recommended placement in `<head>`:**

```html
<head>
  ...
  <!-- i18n:hreflang -->
</head>
```

**Recommended placement before `</body>`:**

```html
  <!-- i18n:translations -->
  <script type="module" src="./assets/js/main.js"></script>
</body>
```

## JavaScript runtime helper

When `<!-- i18n:translations -->` is present, the full translations object is embedded in the page as `window.__i18n` **before** your JS bundle loads.

Import the `t()` helper anywhere in your JavaScript:

```js
import { t, locale } from './i18n.js';

// Translate a key at runtime
document.querySelector('#greeting').textContent = t('hero.heading');

// Get the current locale code
console.log(locale()); // "cs" / "en" / ...
```

### API

#### `t(key: string): string`

Resolves a dot-notation key against `window.__i18n`.  
Returns the key itself (never throws) when the key is not found, and logs a console warning.

```js
t('hero.button')       // → "Click and check console!"
t('footer.builtWith')  // → "Built with ❤️ using Franklin's web devstack."
t('does.not.exist')    // → "does.not.exist"  + console.warn
```

#### `locale(): string`

Returns the active locale code.  
Priority: `window.__i18n.lang` → `<html lang="...">` → `"en"`.

## Build commands

### Production – all locales

```bash
npm run build:i18n   # standalone
npm run build        # full pipeline: includes build:i18n between build:static and build:rev
```

Output:

```
dist/
  index.html          ← en (default)
  cs/
    index.html        ← cs
```

### Production – single locale

Pass `--locale=<code>` to process only one language. The output always goes to `dist/` root (same behaviour as dev mode).

```bash
npm run build:i18n --locale=en   # English only → dist/
npm run build:i18n --locale=cs   # Czech only  → dist/
```

Useful when you want to quickly regenerate just one language without touching the others (e.g. after updating a single JSON file).

### Development – single locale

```bash
npm run dev               # uses defaultLocale from package.json (en)
npm run dev --locale=cs   # Czech
npm run dev --locale=en   # English
```

In dev mode the selected locale is always written to `dist/` root so the live-server can serve it without any path changes.  
The file watcher (`chokidar`) also watches `src/locales/**`, so saving a JSON file instantly rebuilds the HTML.

## Adding a new language

1. Create `src/locales/<code>.json` with all the required keys (copy from an existing file and translate).
2. Run `npm run build:i18n` (or just save any file while `npm run dev` is running).
3. The new locale is automatically picked up – no config changes needed.

---

## Build pipeline position

```
clean → build:css → build:js → build:static → build:i18n → build:rev
                                     ↑                ↑
                          copies raw HTML      applies translations
                          to dist/             & hreflang to dist/
```

`build:i18n` runs **after** `build:static` (so the raw HTML is already in `dist/` as a base) and **before** `build:rev` (so asset hashes are applied to already-translated files).

---

## hreflang tags

The script automatically generates `<link rel="alternate">` for every locale in `src/locales/`, plus an `x-default` pointing to the default locale.

Example output (with `siteUrl = "https://example.com"`, two locales):

```html
<link rel="alternate" hreflang="cs"        href="https://example.com/index.html" />
<link rel="alternate" hreflang="en"        href="https://example.com/en/index.html" />
<link rel="alternate" hreflang="x-default" href="https://example.com/index.html" />
```

If `siteUrl` is not set, the `href` values will be root-relative (e.g. `/index.html`).

---

## Tips

- Keep translation values as plain text where possible. HTML is allowed inside values (e.g. `<code>` tags) but be careful with quoting – JSON strings must use `\"` for embedded double-quotes.
- Translation values are inserted **verbatim** (no escaping), so they can contain any valid HTML fragment.
- Want to share a key across locales (e.g. a brand name)? Put it in every JSON file with the same value – there is no fallback chain by design, to keep things explicit.
